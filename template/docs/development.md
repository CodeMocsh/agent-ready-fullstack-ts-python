# Development

## The two halves

`frontend/` is everything pnpm touches; `backend/` is everything uv touches. Each is
self-contained: it installs, lints, tests and builds without the other's toolchain
present. The root `Makefile` fans out to both, and there is no root `package.json` — a
`pnpm install` at the top level is meant to fail.

| | frontend | backend |
|---|---|---|
| runtime | Node 24 | Python 3.12 |
| package manager | pnpm | uv |
| source | `frontend/src/` | `backend/app/` |
| tests | vitest + Playwright | pytest |
| lint | biome + tsc | ruff + basedpyright + codespell |

## Running it

```bash
make dev            # both halves: backend :8000, frontend :5173 in live mode
make dev-frontend   # frontend only, mock mode -- no backend, no Python
make dev-backend    # backend only, with reload
```

`make dev` starts uvicorn, waits for it to answer, then starts Vite in live mode and
hands your terminal to it. Stopping it stops both. If you would rather have two
terminals, run `make dev-backend` in one and `pnpm -C frontend dev:live` in the other.

### Mock mode and live mode

Mock mode is not a scaffold to delete later. It is how the frontend runs with no backend
and how every component test gets its fixtures.

| | mock mode | live mode |
|---|---|---|
| command | `make dev-frontend` | `make dev` |
| env file | `.env.development`, `.env.mock` | `.env.live` |
| `VITE_ENABLE_MSW` | `true` | `false` |
| who answers `/api/*` | `frontend/src/mocks/handlers.ts` | the backend half |

A running backend does not override the mock handlers: if MSW is enabled, the service
worker answers and your backend changes appear to do nothing. If edits to `backend/` seem
to have no effect, check which mode you are in.

### Ports and the proxy

The backend serves bare paths (`/tasks`). The `/api` prefix is deployment topology, not
part of the contract: the client adds it, and the Vite dev server strips it again on the
way through.

```ts
// frontend/vite.config.ts
proxy: { "/api": { target: "http://localhost:8000", rewrite: (p) => p.replace(/^\/api/, "") } }
```

Two consequences worth knowing:

- **No CORS configuration ships**, because the browser only ever talks to one origin. If
  you deliberately point `VITE_API_BASE_URL` at another origin, add
  `CORSMiddleware` in `backend/app/main.py` yourself.
- **`pnpm preview` has no proxy.** It serves a production build and nothing answers
  `/api`. To look at a real build against a real backend, put a reverse proxy in front of
  both, or use `make dev`.

The ports live in two files — `frontend/vite.config.ts` and `devtools/dev.sh` — and must
agree. Changing them is a two-line edit.

## The contract

```
backend/app/{models,routes}.py  ->  openapi.json  ->  frontend/src/api/schema.ts
```

`make openapi` runs both steps: it exports the spec from the FastAPI app in-process (no
server is started) and regenerates the TypeScript types from it. Both outputs are
committed, which is what lets each half work without the other installed.

```bash
make openapi        # regenerate both artifacts
make openapi-check  # fail if the committed artifacts are stale
```

CI splits the check so neither job needs the other toolchain: the backend job regenerates
the spec from the code and diffs it, the frontend job regenerates the types from the spec
and diffs those.

`frontend/src/api/schema.ts` is generated by `openapi-typescript`, which is run through
`pnpm dlx` at a pinned version rather than installed as a dependency. It needs TypeScript
5 and this project is on TypeScript 7, where the compiler API it uses no longer exists.
`pnpm dlx` gives it its own copy. Bump that pin deliberately — a floating version would
silently rewrite a committed artifact.

### Keeping the two implementations honest

`frontend/src/mocks/handlers.ts` and `backend/app/routes.py` implement the same contract,
and two things stop them drifting.

**At compile time**, the handlers are typed against the spec by `openapi-msw`. An
undeclared status code, a wrong response shape, or a path the backend does not serve is a
type error.

**At run time**, `frontend/tests/contract.test.ts` runs against both:

```bash
pnpm -C frontend test    # includes the contract suite against the mock handlers
make test-contract       # the same file again, against the backend half
```

The second starts both halves and points the client at `http://localhost:5173/api`, so
one pass covers the proxy, the prefix rewrite, real HTTP and the real store. That suite
asserts shapes and status codes only, never seed data: the two implementations seed
different rows on purpose, because seeds are convenience and the spec is the contract.

`make test` runs everything, including that second pass. `make test-fast` skips it.

The contract suite is not in CI, which keeps both jobs single-toolchain. It runs from the
pre-commit hook instead, where both toolchains are already present. To enforce it in CI,
add a third job:

```yaml
  contract:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@08c6903cd8c0fde910a37f88322edcfb5dd907a8 # v5.0.0
        with: { persist-credentials: false }
      - uses: pnpm/action-setup@a7487c7e89a18df4991f7f222e4898a00d66ddda # v4.1.0
      - uses: actions/setup-node@a0853c24544627f65ddf259abe73b1d18a591444 # v5.0.0
        with: { node-version: "24", cache: pnpm, cache-dependency-path: frontend/pnpm-lock.yaml }
      - uses: astral-sh/setup-uv@e92bafb6253dcd438e0484186d7669ea7a8ca1cc # v6.4.3
        with: { version: "0.9.7", enable-cache: true }
      - run: make install
      - run: make test-contract
```

### Things the spec contains on purpose

- **`422` on every route with a parameter or a body**, with `HTTPValidationError` and
  `ValidationError` schemas. FastAPI adds them and they describe real behaviour.
- **A `model` on every error response.** Without one the spec claims the response has no
  body while `HTTPException` returns `{"detail": ...}`.
- **`separate_input_output_schemas=False`.** With the default, a model whose input and
  output schemas differ is emitted twice, as `Task-Input` and `Task-Output`, and the
  aliases in `src/api/types.ts` break.
- **`redirect_slashes = False`.** With redirects on, `/api/tasks/` answers with a 307
  whose `Location` is the backend's own origin — escaping the proxy and failing CORS in a
  browser, far from the cause.

If `openapi.json` or `schema.ts` conflict in a merge, take either side and run
`make openapi`. Never hand-merge them.

## Tests

```bash
make test                       # everything
make test-fast                  # both halves, without the cross-half suite
pnpm -C frontend test:watch     # component tests, watch mode
cd backend && uv run pytest -q  # backend only
```

Component tests run against the mock handlers, so they need no backend. Backend tests use
FastAPI's `TestClient`, so they start no server.

### End-to-end

```bash
pnpm -C frontend exec playwright install chromium   # once per machine
pnpm -C frontend test:e2e                           # mock-mode specs
```

The default Playwright run builds in mock mode and serves it from a **subpath**, because
plenty of hosts do and everything that only works at `/` fails there — the service
worker's scope, the API base, the router basepath. Run it after touching routing, the API
client or the worker setup.

For the real system, start `make dev` and run the live spec:

```bash
pnpm -C frontend exec playwright test --config playwright.live.config.ts
```

Neither runs in CI: the browser download is slow and the mock-mode suite is the one that
would gate. That is a deliberate trade, and it makes these specs yours to keep honest.

## Git hooks

`make hooks` (run for you by `make install`) installs a shim per committed hook into this
clone's hooks directory. It does **not** set `core.hooksPath`: that key is shared by every
worktree of the repository and replaces hook lookup wholesale, so it would disable hooks
other tools installed. A hook you already had is chained rather than overwritten.

The pre-commit hook lints both halves and skips a half whose toolchain is missing, so a
clone that has installed only one still commits.

## Supply chain

Both halves enforce a 14-day cool-off: a release younger than that is not considered
during resolution, which is the window in which most malicious publishes are caught.

- **frontend** — `minimumReleaseAge: 20160` in `frontend/pnpm-workspace.yaml`, plus
  `trustPolicy: no-downgrade`, which fails when a package's publish evidence gets weaker
  than the version you already have. Install scripts are blocked except for msw, which
  needs one to keep its service worker in step with the library.
- **backend** — `exclude-newer = "14 days"` in `backend/pyproject.toml`, repeated in the
  root `Makefile` and in CI because uvx and tool invocations run outside project
  discovery.

**The two are not equally protected, and it is worth knowing which way.** pnpm also
checks publish evidence and blocks install scripts; uv has no trust-evidence check at all,
so the cool-off is the only mechanical gate on a Python dependency. Read the release notes
and the changelog before adding one, because nothing else will.

A consequence of the cool-off: a dependency floor equal to the newest release cannot
resolve, since the only version satisfying it is younger than the window. When bumping,
pick a version published more than a fortnight ago.

Both lockfiles are committed and CI installs with `--frozen-lockfile` and `--frozen`.

## Deploying

Not configured, deliberately — deployment shape is yours. The pieces:

- `make build` produces `frontend/dist/`, a static bundle. Serve it from any static host
  with an SPA fallback (every unknown path returns `index.html`).
- The backend runs under any ASGI server: `uvicorn app.main:app --host 0.0.0.0 --port 8000`.
- Point the two at each other one of two ways. Either put a reverse proxy in front of both,
  serving the bundle and forwarding `/api/*` to the backend **with the prefix stripped**,
  which mirrors the dev setup exactly; or host them on separate origins, set
  `VITE_API_BASE_URL` at build time, and add `CORSMiddleware` to the backend.
- If the bundle is served from a subpath, pass `--base=/that/path/` to `vite build`.
- Never ship mock mode: production builds must leave `VITE_ENABLE_MSW` unset.
